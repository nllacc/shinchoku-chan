# 評価 要件定義書

## 1. 目的

評価依頼へのユーザーの返信を簡易に解析して、できた・できなかった・一部できたのいずれかを判定し、Bot の PDS に結果の証明を残す。判定できないときは1回だけ聞き直し、それでも判定できなければ評価入力フォームを案内し、答えが得られないまま期限が来たら未評価として締める。

## 2. スコープ

### 2.1 対象

- 返信文の語による判定と、語の辞書の追加。
- 結果レコードの作成と、受け取りの返信。
- 聞き直しと、フォームの案内。
- 評価の期限切れの締め。
- フォームで作られた回答レコードの受理と、受理の内容の公開。

### 2.2 対象外

- 評価依頼の投稿。
- 点数やランキングの算出。
- 画面の表示。

## 3. 前提

- 前提: platform — 通知の受信、保存先、Bot の投稿、キーの導出を使う。
- 前提: lexicon — 結果と回答のレコードの検証を使う。

## 4. 機能要件

- FR-1: 評価待ちの投稿への返信の本文を、結果の種別ごとの語の辞書で照合し、種別を判定する。
- FR-2: 辞書は種別の追加と語の追加を設定ファイルだけで行え、複数の種別の語を含む返信は辞書の並び順で先に当たった種別とする。
- FR-3: 判定できたとき、返信を根拠にした結果レコードを Bot の PDS に作り、評価待ちと残りの計画を閉じ、受け取りの返信を送る。
- FR-4: 評価依頼への最初の返信が判定できないときは、できたかできなかったかを尋ねる聞き直しを返信し、聞き直しを評価待ちにする。
- FR-5: 聞き直しへの返信も判定できないときは、評価入力フォームの URL を返信し、その評価待ちを閉じる。
- FR-6: 評価の期限切れの時刻に結果がなければ、未評価の結果レコードを作り、評価待ちと残りの計画を閉じる。
- FR-7: フォームで作られた回答レコードの URI を受け取り、公開レコードを CID 照合して検証し、持ち主が一致すれば、回答を根拠にした結果レコードを作る。
- FR-8: 結果が既にある受理に対する返信や回答は、結果を増やさず無視または拒否する。
- FR-9: フォームの表示のために、受理の内容と結果の有無を、受理のキーから返す。

## 5. 非機能要件

- NFR-1: 代表的な30文の返信の判定が、すべて期待した種別になる。
- NFR-2: 返信1件の処理が発生させる Bluesky への通信は、3回以内である。

## 6. 受け入れ条件

- AC-1 (FR-1): 「できた!」はできた、「終わらなかった…」はできなかった、「半分くらい」は一部できたと判定される。
- AC-2 (FR-1): どの語も含まない返信は、判定できないと判定される。
- AC-3 (FR-2): 辞書に新しい種別とその語を設定ファイルで足すと、コードの変更なしにその種別が判定される。
- AC-4 (FR-2): 「一部できた」は、できたの語を含んでいても一部できたと判定される。
- AC-5 (FR-3): 判定できた返信に対し、返信を根拠にした結果レコードが1件作られ、評価待ちと残りの計画が閉じ、受け取りの返信が送られる。
- AC-6 (FR-4): 評価依頼への判定できない返信に対し、聞き直しが返信され、聞き直しが評価待ちになり、評価依頼の評価待ちは閉じる。
- AC-7 (FR-5): 聞き直しへの判定できない返信に対し、フォームの URL を含む返信が送られ、評価待ちが閉じ、結果は作られない。
- AC-8 (FR-6): 期限切れの時刻に結果がない受理には未評価の結果が作られ、結果がある受理には何も作られない。
- AC-9 (FR-7): CID が一致する回答は結果になり、一致しない回答と、他人の受理への回答は拒否される。
- AC-10 (FR-8): 結果が既にある受理への返信を再処理しても、結果レコードは1件のままである。
- AC-11 (FR-8): 結果が既にある受理への回答は、拒否される。
- AC-12 (FR-9): 受理のキーから、内容・期限日・結果の有無が得られ、存在しないキーは見つからない応答になる。
- AC-13 (NFR-1): 試験用に用意した30文を判定すると、全件が期待した種別と一致する。
- AC-14 (NFR-2): 返信1件の処理で、Bluesky への通信が3回以内である。
