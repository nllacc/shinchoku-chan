# architecture と PoC の手順

`docs/architecture.md`（アーキテクチャ設計書）と `poc/<テーマ>/README.md`（PoC）を扱うときの手順と判断基準である。ルールの一覧は `rules.md`、雛形は `templates/architecture.md`・`templates/poc-readme.md` にある。

## 1. 位置づけ

- architecture.md は **下流の文書**である。正本は spec と PoC であり、architecture.md は両者の内容を人間が読める形に要約して構造を示す。矛盾したときは spec を正とする。
- 書けるのは、**根拠のある確定した内容だけ**である。根拠は spec 名か `poc/<テーマ>` で、技術基盤と横断的制約の各行に必ず書く（S013 が実在を検査する）。根拠のない決定は書けない。
- 複数の spec にまたがる流れ・境界・技術基盤の理由は、architecture.md が単独の記述を持てる（機能・信頼と検証・技術基盤）。個別の値やルールは spec にあり、architecture.md に複製しない（W014 が重複を検出する）。
- 経緯・却下案・日付・検証手順は書かない（W009）。PoC の実測の詳細は `poc/<テーマ>/` に置く。

## 2. 新規開発の手順

1. **構想の聞き取り**: サービスの構想を聞く。アーキテクチャの案が出ても確定扱いにせず、検証すべき仮説として扱う。
2. **PoC**: 技術的なリスク（外部サービスの挙動・性能・料金枠・認証方式など）を `poc/<テーマ>/README.md` の「4. 検証項目」に仮説と合格基準として書き、検証して結果（合／否）を記入する。PoC のために spec は作らない（spec は確定した仕様だけを書く文書である）。
3. **確認と提案**: 結果を人間へ提示し、構想の修正や検証項目の追加を受ける。**修正や追加があれば 2 へ戻る**。README は最新の状態に上書きし、履歴は git に任せる。終了条件は、全検証項目に結果が付き、人間が結論を承認したことである。
4. **spec の作成**: 確定した内容で `specs/` を作る（SKILL.md の手順どおり）。実装中に仮説が崩れたら 2 へ戻る（反映先は既存 spec）。
5. **architecture.md の作成**: 雛形から作る。根拠は spec か PoC とする。
6. **承認**: 内容を人間へ提示し、承認を得てから確定する（機械検証できないため、手順として守る）。`npm run lint:spec` を通す。
7. **PoC の完了**: 反映先 spec の全タスクが完了したら、5 節の手順で根拠を spec へ付け替え、PoC を削除する。

## 3. 既存プロジェクトの手順

PoC は必須ではない。根拠はすべて spec にする。

1. **現状の把握**: `npm run lint:spec -- --status` で spec の状態を確認し、`npm run lint:spec` を通す。全タスクが完了した spec は、構成表のパス・テストの実在で実装との乖離を検出する（S006〜S008）。
2. **architecture.md の作成**: 雛形から作る。実装と spec を調査し、構成要素・外部インターフェース・機能を spec に基づいて書く。
3. **承認**: 内容を人間へ提示し、承認を得てから確定する。
4. **再検証の要否の判断**: 次のときは再検証が必要になりうる。人間と相談して決める。
   - lint が実装との乖離を検出した（S006〜S008）。
   - 依存や実行環境の版が変わり、前提とした挙動が変わりうる。
   - 外部連携や構成要素を追加する。
5. **再検証が要るとき**: 新規開発の 2・3 の反復を行う。反映先は既存の spec とする。結果に基づいて spec を更新し、architecture.md を更新する。

機械で検出できるのは、architecture ↔ spec の突合（S012・S013）と、spec ↔ 実装の整合（S006〜S008）である。**他コンポーネントとの噛み合いや、挙動が設計どおりかは機械では判定できない**。再検証の判断は人間が行う。

## 4. PoC の README

`poc/<テーマ>/README.md` は固定の章立てで、先頭の「結論」「反映先」「制約値」だけを読めば足りる。手順・ログ・コードなどの詳細は README の外のファイルに置き、「5. 手順と結果」からリンクする（README の外は検査しない）。

- **1 PoC = 1 テーマ = 反映先 1 件**。複数の spec にまたがる仮説は、制約を持つ主たる spec を選ぶか、テーマを分ける。
- **状態は成果物から導出する**（宣言しない）。
  - 検証中: 結論が「- なし」、または検証項目の結果に「-」が残っている。
  - 反映待ち: 結論があり、反映先が「- なし」。
  - 反映済み: 反映先に spec がある。その spec の全タスクが完了していれば削除対象になる。
- 結論は、全検証項目の結果が「合」「否」になってから書く（F-P08）。
- 反映済みでない PoC は、設定の件数（初期 3）を超えて溜められない（S017）。

## 5. PoC の完了と削除

反映先 spec の全タスクが完了すると、S016（削除）と S018（根拠の付け替え）が指摘される。次の順で行う。

1. `npm run lint:spec -- --retarget-poc <テーマ>` で、根拠 `poc/<テーマ>` が反映先 spec に置き換わる差分を確認する。問題なければ `--write` を付けて適用し、`npx prettier --write docs` で表を整える。
   - 置換先は PoC の反映先（1 件）で一意に決まる。置換先の spec が行の主張を本当に支えているかは、目視確認の項目 5 で確認する。
2. `npm run lint:spec -- --check-poc-committed <テーマ>` を実行する。**終了コードが 0 でなければ削除しない**。
   - 1（未コミットの変更あり）／2（git の追跡外）のときは停止し、ユーザーにコミットを依頼する。ユーザーがそのセッションで明示的にコミットを許可している場合だけ、Claude がコミットしてから進める。
   - 削除しても内容は git の履歴に残る。履歴に入っていない PoC を削除すると、内容が失われる。
3. `poc/<テーマ>/` を削除し、`npm run lint:spec` を通す（根拠の付け替え漏れは S013 が検出する）。

### コミットの扱い

- リポジトリのスキルや CLAUDE.md に注意書きがない限り、コミットだけなら許可する（差分の消失を避けるため）。**push は含まない**。push はユーザーの許可を得る。
- 作業ブランチが本番向けでないか（CI の対象でないか）の判断は、本スキルの対象外である。リポジトリのスキルや CLAUDE.md の指示に従う。

## 6. architecture.md の書き方

- **章立ては固定**（1〜9 章）。該当しない章は「- なし」と書く（構成要素は不可）。
- 構成要素は **spec 単位ではなく実行単位・論理単位**で書く。複数の spec が1つの構成要素を実装してよい。すべての設計済み spec が、いずれかの構成要素の「実装spec」にちょうど1回現れる（S012）。
- 外部インターフェースは、システム境界を越える通信を 1 行 1 IF で書く。方式は通信の種類とデータ形式、認証は通信相手の確認方法を書く。受け取った内容の検証は「7. 信頼と検証」に書く。
- 機能は「複数の構成要素が協調して達成する振る舞い」の単位で H3 を切る。1 機能に関与する構成要素は 2〜6 件にする。多いときは機能を分ける。関与の集合と図のメッセージ名の集合がどちらも似ている機能（類似度 0.8 以上）は、同じ振る舞いの重複とみなして統合する（関与が同じでも、メッセージが違えば別の機能である）。
- 図は構成要素の名前をそのままノード名にする。外部の構成要素は ID を `ext_` で始める。
- 文は主語を省略せず、「。」で終わる 1 文で書く（W010・W012）。指示語（これ・それ・同様・上記など）は使わず、指す対象を名前で書く（W011）。
- 文書が長くなったら（400 行超）、機能（H3）を `docs/architecture/<機能>.md` に分け、5 章を「- [機能名](architecture/<名>.md): 説明。」の索引にする。分割は機能単位で行い、行数で途中分割しない。分割の判断は F-A13、機能の切り方の妥当性は目視確認で確認する。

## 7. 目視確認（Claude が実施する）

`lint:spec` が合格した後、次を上から順に 1 回ずつ数える。判定は「該当数が 0」か否かのみで行い、好みの指摘は加えない。該当が 0 件なら変更しない（同じ入力には同じ結論になる）。

1. 構成要素表の責務が、実装spec の要件の目的と食い違う行の数。
2. システム構成の関係図のエッジのうち、実装spec の設計に呼び出しの根拠がないものの数（外部とのエッジは数えない）。
3. 機能のワークフロー図のメッセージのうち、関与する構成要素の実装spec に対応する処理がないものの数。
4. 同じ事実を複数の章が述べている組の数。
5. 根拠が spec の行で、その spec の内容と値が食い違う行の数（PoC から付け替えた行を含む）。
6. 外部インターフェースの方式・認証が、内部の要素の実装spec と食い違う行の数。
7. 機能の切り方が妥当でない数（1 つの機能が複数の独立した振る舞いを含む、または 1 つの振る舞いが複数の機能に分かれている）。
8. 移行時のみ: 旧文書にあって新文書にも spec にもない決定事項の数。

## 8. 要件のみの spec

要件は確定しているが、設計・実装に着手していない将来の機能は、`specs/<名>/requirements.md` だけを置く。

- 状態は `--status` が「要件のみ」と導出する（進捗の語は書かない）。要件は、実装の有無に依存しない形で書く（SKILL.md の requirements.md の原則）。
- 設計に着手するとき、design.md と tasks.md を**両方**追加する（S003）。
- architecture.md の「実装spec」には載せない（S012）。spec 数の閾値（S010）にも数えない。

## 9. 設定（`.spec-driven.json`）

リポジトリ直下に置く任意のファイルである。調整できるのは数値だけで、語彙・図の記法・章立てなどの質的なルールは調整できない。範囲外の値や未知のキーはエラー（終了コード 2）になる。実効値は `npm run lint:spec -- --show-config` で確認する。雛形は `templates/spec-driven.json`（初期値と同じ）。

| キー                            | 初期値 | 許容範囲                                                                           |
| ------------------------------- | ------ | ---------------------------------------------------------------------------------- |
| architecture.minSpecs           | 3      | 1〜50（設計済み spec がこの件数以上なら architecture.md が必須。無効化はできない） |
| architecture.maxLines           | 400    | 200〜800                                                                           |
| architecture.maxFunctionLines   | 80     | 40〜150                                                                            |
| architecture.functionComponents | [2, 6] | 各 2〜10（最小 ≦ 最大）                                                            |
| architecture.mergeSimilarity    | 0.8    | 0.5〜1.0                                                                           |
| poc.maxReadmeLines              | 100    | 50〜200                                                                            |
| poc.maxPending                  | 3      | 1〜10                                                                              |

## 10. 既存の architecture.md の移行

1. 旧文書の各決定事項を、spec にあるか・PoC の制約値にするか・削除するかに分類する。
2. spec にも PoC にもない決定事項で、現在も有効なものは、先に該当 spec に追記する（architecture.md は根拠のない決定を書けない）。
3. 経緯・却下案・日付・進捗・検証手順は削除する（履歴は git に残る）。
4. 将来の機能で要件が確定しているものは、要件のみの spec にする（8 節）。
5. 雛形から作り直し、`npm run lint:spec` を通し、目視確認の項目 8 まで実施する。
